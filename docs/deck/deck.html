Innovation & Use Case Relevance · 30%

The rubric asks: “Is the use case a credible, realistic application of IBM Bob (vs. a generic project that happens to touch it)?”

A realistic job for Bob: legacy code that runs a real phone line

The legacy system

  • telephony-console.py: 11,858 lines in one file, with hand-rolled routing
  • It shells out for every read: 11 call sites (analysis §4)
  • fax/cli.py: 288 lines around Asterisk SendFax, no tests
  • In production on the house PBX: status, the fax log and sending must keep working

Real legacy, real stakes

Framework-free production code. The track's own list is the work: structure, tests, an API, modernization docs.

Safe by construction

Bob works in an OS sandbox with no network. In run 5 it tried git stash; the read-only .git refused it.

No private data reached an AI tool

Every prompt passes the scrub gate first. Fixtures use 555-01xx numbers and example.com hosts.

The pattern carries over to any single-file admin tool: put one seam in front of the live system, record fixtures behind it, and the tool becomes testable and safe to demo.

Presentation & Clarity · 10%

The rubric asks: “Can the team clearly explain what they built and how Bob was used in a few minutes?”

In one minute, and how to check it yourself

What we built

A house PBX's legacy fax tools, modernized without taking the phone line down: a typed, tested faxcli package, and the Fax panel as a small typed API (faxconsole) behind one Asterisk adapter, with a replay mode.

How Bob was used

Bob wrote the analysis, the package and its tests, and fixed most of what review found (Bob factor bob.factor_pct), headless, inside an OS sandbox, with every run recorded.

Improvements made in the window

Commit #1 is the pre-hackathon baseline, scrubbed and otherwise unchanged, rebuilt once on day one. Everything after it is new. Bob wrote most of the code and tests. Claude wrote the scrub gate, CI, the sandbox and the ledger, plus a few small review fixes, each in its own commit with a test.

Future roadmap · key learnings and next steps

What we learned, and what's next

Learned

  • Scrub before the first prompt. The baseline was cleaned of numbers, names and hosts before any AI tool saw it, and a pre-commit check keeps it that way.
  • Review Bob against the code. The analysis's most important finding, a PBX that cannot be read reported as ok: true, came from review, not from Bob.
